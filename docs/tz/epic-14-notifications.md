# E14. Уведомления

Приоритет: **must-have** (пуши и почта), **nice-to-have** (Telegram-бот). Порядок реализации: **14**.

---

## Цель эпика

Возвращать человека в приложение, когда произошло что-то, требующее его участия.

Проблема, которую решает эпик: в этом продукте скорость ответа решает — курьер улетает через три дня, и переписка, замеченная через неделю, бесполезна. При этом веб-клиент полноценный, с чатом и сделками, а веб-пуши в MVP не делаются: на iOS они работают плохо и ненадёжно. Значит, у веб-пользователей должен быть свой надёжный канал.

---

## Пользовательские сценарии

- Как курьер, я хочу узнать об отклике сразу, чтобы ответить, пока человек не ушёл к другому.
- Как пользователь, я хочу получить уведомление о новом сообщении, чтобы не проверять приложение каждый час.
- Как заказчик, я хочу получить напоминание, что срок хранения заканчивается, чтобы не потерять посылку.
- Как пользователь веба, я хочу узнавать о событиях, хотя пушей в браузере нет.
- Как пользователь, я хочу отключить то, что мне не нужно, чтобы приложение не превращалось в шум.
- Как пользователь в Нячанге, я не хочу получать уведомления ночью из-за того, что в Москве ещё день.

## Функциональные требования

### Каналы

14.1. Три канала доставки:

| Канал | Реализация | Платформы |
|---|---|---|
| Пуш-уведомления | APNs для iOS, FCM для Android | Мобильные |
| Электронная почта | Транзакционная рассылка | Все |
| Telegram-бот | Bot API | Все |

14.2. Веб-пуши в MVP не реализуются. Веб-пользователь получает уведомления почтой и в Telegram.

14.3. Telegram привязывается один раз по ссылке с одноразовым токеном. Привязка переиспользуется входом через Telegram (E03), если он уже выполнен.

14.4. **Telegram-бот помечен как nice-to-have** и режется первым при нехватке времени (см. E00). Пуши и почта — обязательный минимум.

### События

14.5. Перечень событий и каналов по умолчанию:

| Событие | Пуш | Почта | Telegram | Срочное |
|---|---|---|---|---|
| Новое сообщение в чате | да | нет | да | да |
| Новый отклик на объявление | да | да | да | да |
| Сделка создана | да | да | да | да |
| Смена статуса сделки | да | да | да | да |
| Требуется переподтверждение при перевесе | да | да | да | **да** |
| Напоминание о сроке хранения | да | да | да | да |
| Запрос на продление хранения и ответ на него | да | да | да | да |
| Срок хранения истёк, сделка проблемная | да | да | да | да |
| Совпадение по подписке на маршрут | да | да | да | нет |
| Результат верификации | да | да | да | да |
| Решение по жалобе | да | да | да | нет |
| Предупреждение от модератора | да | да | да | да |
| Напоминание оставить отзыв | да | нет | да | нет |
| Опубликован отзыв о вас | да | нет | да | нет |
| Ответ поддержки | да | да | да | да |

14.6. Событие доставляется по всем включённым каналам одновременно, без дублирования внутри канала.

### Настройки

14.7. Пользователь управляет каналами по группам событий: сообщения, сделки, объявления и подписки, сервисные уведомления.

14.8. Полное отключение канала доступно. Отключить уведомления о **сделках** нельзя: это события, требующие действия, и их пропуск ломает сделку для второй стороны.

14.9. Настройки хранятся на сервере и действуют на всех устройствах.

### Тихие часы

14.10. Несрочные уведомления не доставляются с **23:00 до 08:00 по местному времени пользователя** и отправляются утром.

14.11. Часовой пояс определяется по городу из профиля (E06, справочник E05), при отсутствии — по настройке устройства, при отсутствии — Europe/Moscow.

14.12. Срочные события (столбец «Срочное» в 14.5) доставляются немедленно независимо от времени. Требование переподтверждения при перевесе — всегда срочное: человек стоит на встрече и ждёт.

14.13. Тихие часы актуальны именно для этого продукта: между Москвой и Нячангом четыре часа разницы, и без них половина уведомлений приходила бы ночью.

### Группировка

14.14. Сообщения из одного чата группируются: несколько подряд дают одно уведомление со счётчиком.

14.15. Совпадения по подписке на маршрут группируются в часовое окно (E08).

14.16. Уведомление о новом сообщении не отправляется, если чат открыт на активном устройстве.

### Доставка и надёжность

14.17. Отправка выполняется асинхронно и не блокирует основной сценарий: неудача доставки не должна ломать смену статуса сделки.

14.18. При ошибке доставки выполняется до трёх повторов с нарастающим интервалом. Недоставленное уведомление записывается с признаком ошибки.

14.19. Недействительный токен устройства удаляется, канал для этого устройства отключается.

14.20. Все отправки логируются в таблицу `notifications`: получатель, событие, канал, время, результат.

14.21. Внутри приложения есть список уведомлений с отметкой прочтения — на случай, если внешний канал не сработал.

### Содержание

14.22. Текст уведомления не раскрывает содержимого личной переписки: показывается имя отправителя и факт сообщения, не текст. Уведомление может отображаться на заблокированном экране постороннему.

14.23. Уведомление содержит ссылку, открывающую нужный экран приложения напрямую (deep link).

14.24. Тексты уведомлений живут в файлах локализации (E02), а не в коде.

## Критерии приёмки

- [ ] Пуши приходят на iOS и Android для всех событий из таблицы
- [ ] Письма приходят и корректно отображаются в основных почтовых клиентах
- [ ] Telegram привязывается по ссылке, уведомления приходят
- [ ] Настройки по группам событий сохраняются и действуют на всех устройствах
- [ ] Отключить уведомления о сделках невозможно
- [ ] Несрочное уведомление в 02:00 по местному времени пользователя откладывается до утра
- [ ] Срочное уведомление в 02:00 доставляется немедленно
- [ ] Часовой пояс берётся из города профиля; при его отсутствии работает запасной вариант
- [ ] Три подряд сообщения из одного чата дают одно уведомление со счётчиком
- [ ] Уведомление не приходит, если чат открыт на активном устройстве
- [ ] Ошибка доставки не мешает смене статуса сделки
- [ ] Недействительный токен устройства удаляется
- [ ] Текст сообщения не раскрывается в уведомлении
- [ ] Переход по уведомлению открывает нужный экран
- [ ] Список уведомлений в приложении содержит все события

## Технические детали и ограничения

**APNs** требует сертификата или ключа Apple Developer, **FCM** — проекта Firebase. Оба нужны заранее: получение доступов занимает время, которое лучше потратить параллельно разработке.

**Транзакционная почта** отправляется через внешний сервис (Resend, Postmark или аналог). Важно: доставляемость до российских почтовых доменов требует настроенных SPF, DKIM и DMARC — без них письма попадут в спам, и канал окажется бесполезным.

**Отложенная отправка** тихих часов реализуется полем «отправить не раньше» и фоновой задачей, а не задержкой в памяти процесса.

**Telegram-бот** используется здесь только как канал доставки. Уведомление модератору о новом обращении в поддержку (E15) идёт через него же.

**Таблицы эпика:** `notifications`, `notification_settings`, `device_tokens`, `telegram_links`.
