# E01. Фундамент и инфраструктура

Приоритет: **must-have**. Порядок реализации: **1** (параллельно с E02).

---

## Цель эпика

Создать техническую основу, на которой строятся все остальные эпики: репозиторий, окружения, базу данных с механизмом миграций, слой доступа к данным, контракт API и единые соглашения об ошибках, логировании и конфигурации.

Проблема, которую решает эпик: при трёх независимых клиентах и одном бэкенде рассинхрон возникает мгновенно, если контракт и соглашения не зафиксированы до начала работы. Кроме того, прямой доступ к базе из бизнес-логики сделает невозможной заявленную заменяемость хранилища.

Пользовательской функциональности в эпике нет.

---

## Пользовательские сценарии

- Как разработчик, я хочу поднять проект одной командой, чтобы не тратить время на настройку окружения при каждом входе в новую задачу.
- Как разработчик, я хочу описывать API один раз в спецификации, чтобы клиентские модели генерировались автоматически и не расходились с сервером.
- Как разработчик, я хочу обращаться к данным через репозитории, чтобы смена хранилища не требовала правок в бизнес-логике.
- Как владелец продукта, я хочу иметь возможность сменить регион размещения данных без переписывания кода, чтобы юридические решения не блокировали разработку.

---

## Функциональные требования

### Репозиторий и структура

1.1. Создать монорепозиторий со структурой:

```
/apps/api          NestJS
/apps/web          Next.js — веб-клиент
/apps/admin        Next.js — админ-панель
/apps/ios          Swift / SwiftUI
/apps/android      Kotlin / Jetpack Compose
/packages/contracts  OpenAPI-спецификация и генерируемые типы
/packages/shared     общие константы и словари локализации
/docs
```

1.2. Настроить менеджер пакетов с рабочими пространствами (pnpm workspaces) для JS/TS-приложений. Мобильные приложения живут в том же репозитории, но собираются своими инструментами.

1.3. Настроить единые правила форматирования и линтинга для TypeScript: ESLint, Prettier, строгий режим TypeScript (`strict: true`).

1.4. Добавить `README.md` в корень с описанием: как поднять окружение, как запустить каждое приложение, как применить миграции.

### Окружения и конфигурация

1.5. Поддержать три окружения: `local`, `staging`, `production`. Каждое описывается набором переменных окружения.

1.6. Все внешние адреса и ключи задаются переменными окружения. Захардкоженных URL, ключей и регионов в коде быть не должно.

1.7. Регион размещения Supabase и адрес проекта задаются переменными `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `SUPABASE_ANON_KEY`. Смена региона выполняется заменой значений, без правки кода.

1.8. Добавить `.env.example` с полным перечнем переменных и комментарием к каждой. Реальные `.env` в репозиторий не попадают.

1.9. Приложение при старте валидирует наличие и формат обязательных переменных окружения и падает с понятным сообщением, если чего-то не хватает.

### База данных и миграции

1.10. Подключить проект Supabase, использовать PostgreSQL как основную базу.

1.11. Настроить механизм миграций (Supabase CLI). Каждая миграция — отдельный файл с меткой времени, изменения схемы вручную через веб-интерфейс запрещены.

1.12. Зафиксировать соглашения о схеме, обязательные для всех эпиков:
- первичный ключ — `uuid`, генерируется на стороне базы;
- у каждой таблицы есть `created_at` и `updated_at` типа `timestamptz`, заполняются автоматически;
- имена таблиц во множественном числе, имена колонок в `snake_case`;
- удаление пользовательских сущностей — логическое, через `deleted_at`, если в эпике не указано иное;
- денежные суммы хранятся целым числом в минимальных единицах валюты (копейки, донги), валюта — отдельной колонкой;
- вес хранится целым числом в граммах.

1.13. Создать базовую таблицу `audit_log` для действий модераторов: кто, что, над каким объектом, когда, с какими значениями до и после.

### Слой репозиториев

1.14. Реализовать слой репозиториев как единственный способ обращения к данным. Сервисы бизнес-логики не содержат SQL и не импортируют клиент Supabase напрямую.

1.15. Каждый репозиторий описывается интерфейсом; конкретная реализация (Supabase) внедряется через DI-контейнер NestJS.

1.16. Реализовать поддержку транзакций на уровне слоя репозиториев: операция, затрагивающая несколько таблиц, выполняется атомарно.

### Контракт API

1.17. Создать спецификацию OpenAPI 3.1 в `/packages/contracts`. Спецификация — источник правды; изменение API без её обновления считается ошибкой.

1.18. Настроить генерацию типов из спецификации: TypeScript для веба и админки, Swift для iOS, Kotlin для Android. Генерация запускается командой и проверяется в CI.

1.19. Зафиксировать формат ответа об ошибке, единый для всех эндпоинтов:

```json
{
  "error": {
    "code": "VERIFICATION_REQUIRED",
    "message": "Для публикации объявления нужно пройти проверку документа",
    "details": {}
  }
}
```

Поле `code` — машиночитаемый идентификатор из фиксированного перечня, `message` — готовый к показу текст на русском.

1.20. Зафиксировать формат постраничной выдачи: параметры `limit` и `cursor`, ответ содержит `items` и `next_cursor`.

1.21. Все даты в API передаются в формате ISO 8601 с указанием часового пояса.

### Логирование и наблюдаемость

1.22. Настроить структурное логирование в JSON. В каждой записи: метка времени, уровень, идентификатор запроса, идентификатор пользователя (если есть), сообщение.

1.23. В логи **не попадают**: содержимое сообщений чата, персональные данные из верификации, значения токенов и ключей.

1.24. Реализовать эндпоинт `/health`, возвращающий состояние сервиса и доступность базы.

### CI

1.25. Настроить сборку в CI для `api`, `web`, `admin`: установка зависимостей, линтинг, типизация, тесты, сборка.

1.26. Настроить проверку соответствия сгенерированных типов текущей спецификации OpenAPI: расхождение ломает сборку.

## Критерии приёмки

- [ ] Репозиторий развёртывается на чистой машине по инструкции из `README.md` без дополнительных вопросов
- [ ] `pnpm dev` поднимает бэкенд, веб-клиент и админку локально
- [ ] Миграции применяются командой, схема воспроизводится с нуля на пустой базе
- [ ] Запуск с неполным набором переменных окружения падает с понятным сообщением, а не с непонятной ошибкой в середине работы
- [ ] Бизнес-логика не содержит ни одного прямого обращения к Supabase — проверяется поиском импортов клиента за пределами слоя репозиториев
- [ ] Спецификация OpenAPI валидна, типы генерируются для трёх платформ
- [ ] Расхождение спецификации и сгенерированных типов ломает сборку в CI
- [ ] `/health` отвечает и корректно показывает недоступность базы, если её остановить
- [ ] В логах отсутствуют персональные данные и секреты при полном прогоне сценария регистрации

## Технические детали и ограничения

**Стек.** NestJS + TypeScript на бэкенде, Next.js для веба и админки, PostgreSQL в Supabase, Supabase Storage для файлов, Supabase Realtime для чата.

**Supabase Auth** используется как провайдер аутентификации, но пользовательские данные приложения живут в собственной таблице `users`, связанной с `auth.users` по идентификатору. Логика доступа реализуется в бэкенде, а не в политиках Row Level Security: правила сложные (машина состояний сделки, условия публикации отзывов, очередь верификации), и три независимых клиента не должны дублировать их каждый по-своему.

**Бесплатный тариф Supabase** засыпает после недели простоя — проект приходится будить вручную. Для этапа обкатки это допустимо, в документации по развёртыванию нужно об этом написать.

**Redis** в MVP не используется: очереди и кеш не нужны при ожидаемой нагрузке. Если понадобятся, вводятся отдельной задачей.
