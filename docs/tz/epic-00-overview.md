# Посылки — сводное описание ТЗ

P2P-сервис попутной доставки посылок для русскоязычных экспатов. Приложение сводит человека, который летит по нужному маршруту и готов взять посылку, с человеком, которому надо эту посылку передать или получить.

Документ описывает состав MVP, порядок реализации эпиков и сквозные решения, обязательные для всех эпиков.

Дата: 31 июля 2026. Статус: утверждено заказчиком.

---

## 1. Роли в продукте

| Роль | Кто это |
|---|---|
| **Курьер** | Везёт посылку. Участник сделки, всегда с приложением |
| **Заказчик** | Вторая сторона сделки, платит за доставку. Всегда с приложением |
| **Передающий** | Физически отдаёт посылку курьеру. По умолчанию заказчик, может быть третьим лицом без приложения |
| **Получающий** | Физически забирает посылку. По умолчанию заказчик, может быть третьим лицом без приложения |
| **Модератор** | Сотрудник сервиса. Работает только в админ-панели |

Со стороны курьера принять и вручить посылку тоже может доверенное лицо. Подтверждения в приложении делают **только участники сделки** — курьер и заказчик. Доверенные лица ничего не нажимают.

Термин «отправитель» в документах не используется: вторая сторона сделки чаще получает посылку, чем отправляет.

### Почему админ-панель стоит пятой

Очередь ручной верификации живёт в админ-панели. Без неё эпик E04 существует, но не работает: ни один пользователь не сможет пройти проверку и, следовательно, ни опубликовать объявление, ни войти в сделку. Откладывать админку на конец нельзя.

### Что режется при нехватке времени

Почти всё в MVP помечено must — объём резался последовательно на этапе проектирования, и лишнего не осталось. Настоящих nice-to-have четыре, все внутри эпиков:

| Порядок реза | Что | Где |
|---|---|---|
| 1 | Telegram-бот как канал уведомлений | E14 |
| 2 | Разбор свободного текста в поля объявления | E13 |
| 3 | ИИ-ассистент первой линии поддержки | E13, E15 |
| 4 | Соседние города в пустой ленте | E08 |

Ядро — E01–E12 — не режется ни при каких обстоятельствах.

## 3. Сквозные решения

Обязательны для всех эпиков. Отклонения возможны только с явным указанием в тексте эпика.

### 3.1. Платформы

- **iOS** — Swift, SwiftUI, минимальная версия iOS 16
- **Android** — Kotlin, Jetpack Compose, минимальная версия Android 9 (API 28)
- **Веб** — Next.js, React, TypeScript
- **Админ-панель** — отдельное приложение Next.js
- **Бэкенд** — NestJS, TypeScript

Клиенты **не ходят в Supabase напрямую**. Единственная точка входа — REST API бэкенда.

### 3.2. Паритет платформ

Мобильные клиенты полные. В веб-клиенте отсутствует работа с камерой: фотографии документов и содержимого посылки загружаются файлом. Всё остальное в вебе доступно.

### 3.3. Уровни доступа

| Действие | Требование |
|---|---|
| Просмотр лент и карточек объявлений | Без регистрации |
| Отправка сообщений в чат | Регистрация |
| Публикация объявления | Пройденная верификация |
| Вход в сделку | Пройденная верификация |

### 3.4. Язык

Интерфейс только на русском. Все пользовательские тексты вынесены в файлы локализации на каждой платформе; захардкоженных строк в коде быть не должно. Добавление языка в будущем — один файл перевода на платформу.

### 3.5. Данные и хранилище

- PostgreSQL в Supabase, доступ **только через слой репозиториев** — прямых запросов к базе из бизнес-логики быть не должно
- Файлы (фотографии, документы) — Supabase Storage
- Реальное время в чате — Supabase Realtime
- Регион размещения задаётся параметром развёртывания и не зашивается в код

### 3.6. Контракт API

Спецификация OpenAPI — единственный источник правды. Пишется до реализации клиентов, из неё генерируются модели для веба, iOS и Android. Изменение контракта без обновления спецификации недопустимо.

### 3.7. Персональные данные

Сканы документов **не хранятся**. После решения модератора файл удаляется из хранилища безвозвратно. В базе остаются: флаг верификации, имя, фамилия, дата рождения, тип документа, хэш номера документа, дата и идентификатор проверки.

### 3.8. Деньги

Расчёты между пользователями идут **мимо приложения**. Сервис не принимает, не хранит и не переводит деньги. Цена фиксируется в объявлении и в сделке как информация, платёжных операций нет.

Модель данных при этом спроектирована под будущий эскроу: у сделки есть цена, валюта, история статусов и подтверждения обеих сторон.

### 3.9. Возраст

Сервисом пользуются лица 18 лет и старше. Проверяется по дате рождения на этапе верификации.

### 3.10. Тихие часы

Несрочные уведомления не доставляются с 23:00 до 08:00 по местному времени пользователя. Часовой пояс берётся из города, указанного в профиле, либо из настроек устройства.

## 4. Справочные величины MVP

**Города (15).** Вьетнам: Нячанг, Дананг, Хошимин, Ханой, Муйне. Россия: Москва, Санкт-Петербург, Новосибирск, Красноярск, Воронеж, Краснодар, Ростов-на-Дону. Казахстан: Алматы, Астана. Киргизия: Бишкек.

Доступна любая пара городов в обе стороны — 210 направлений. Город означает **место передачи посылки**, а не аэропорт: у Муйне своего аэропорта нет, туда добираются из Камрани или Хошимина.

**Валюты (4).** Рубль, донг, сом, тенге. Автоматической конвертации нет, цены отображаются в той валюте, в которой указаны.

**Модель ИИ.** Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) для всех применений: модерация объявлений, модерация описи, разбор свободного текста, первая линия поддержки.

## 6. Как эпик разбивается на задачи

Каждый эпик содержит раздел «Разбивка на задачи»: список задач по 1–3 часа работы ИИ-агента. Порядок внутри эпика: сначала бэкенд, затем веб, iOS и Android — эти три можно вести параллельно.

Каждая задача самодостаточна: её можно передать агенту в отдельной сессии, не пересказывая контекст всего проекта. У задачи есть критерий приёмки и команда проверки.

**Контрольная точка.** Клиентские задачи любого эпика не начинаются, пока не утверждены макеты из E02.
