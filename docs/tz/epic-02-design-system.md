# E02. Дизайн-система и макеты

Приоритет: **must-have**. Порядок реализации: **1** (параллельно с E01).

---

## Цель эпика

Описать визуальный язык продукта один раз для всех платформ и проработать макеты пяти ключевых экранов, на которых расположение элементов реально влияет на понятность.

Проблема, которую решает эпик: независимые клиенты (веб и мобильное приложение), собираемые по отдельности, без общего описания дадут разные приложения. При этом рисовать все экраны отдельно для iOS и Android избыточно — React Navigation воспроизводит нативные соглашения о навигации каждой платформы автоматически, поэтому один макет мобильного экрана достаточен для обеих.

---

## Пользовательские сценарии

- Как пользователь, я хочу видеть согласованный интерфейс, чтобы понимать, что элемент с одинаковым видом делает одинаковое действие на любом экране.
- Как пользователь iPhone, я хочу, чтобы приложение вело себя как приложение iPhone, а не как перенесённый андроид.
- Как владелец продукта, я хочу утвердить внешний вид ключевых экранов до начала разработки клиентов, чтобы не переделывать готовое.
- Как разработчик, я хочу иметь однозначное описание компонентов и их состояний, чтобы не принимать решения о внешнем виде по ходу реализации.

---

## Функциональные требования

### Токены дизайн-системы

2.1. Описать палитру: основной цвет, цвет действия, цвета состояний (успех, предупреждение, ошибка, нейтральное), фоны, границы, текст основной и второстепенный. Для каждого цвета — значение для светлой и тёмной темы.

2.2. Описать типографику: размеры и начертания для заголовков трёх уровней, основного текста, второстепенного текста, подписей. Веб и мобильное приложение используют единую пару шрифтов из утверждённого брендборда — Manrope (заголовки, цифры, акценты) и Inter (основной текст) — вместо системного шрифта платформы: это осознанное решение в пользу брендборда (см. «Технические детали и ограничения»).

2.3. Описать сетку отступов на основе базовой единицы 4 пикселя. Все отступы кратны базовой единице.

2.4. Описать радиусы скругления и тени — по два-три значения, не больше.

2.5. Токены хранятся в `/packages/shared` в машиночитаемом виде (JSON) и переносятся в каждую платформу её средствами: CSS-переменные в вебе, JS/TS-объект темы в React Native.

### Компоненты

2.6. Описать обязательный набор компонентов с перечнем состояний для каждого:

| Компонент | Состояния |
|---|---|
| Кнопка (основная, второстепенная, текстовая) | обычная, нажатая, отключённая, загрузка |
| Поле ввода | пустое, заполненное, в фокусе, с ошибкой, отключённое |
| Выбор из справочника (город, валюта) | закрытый, открытый, с поиском, пустой результат |
| Выбор даты | — |
| Карточка объявления | рейс, заявка |
| Бейдж статуса верификации | проверен, на проверке, не проверен |
| Бейдж статуса сделки | по одному на каждый из статусов E10 |
| Аватар с отметкой верификации | — |
| Рейтинг звёздами | только чтение, ввод |
| Сообщение в чате | своё, чужое, с фото, системное |
| Пустое состояние | с действием, без действия |
| Индикатор загрузки | экран целиком, элемент |
| Сообщение об ошибке | встроенное в форму, на весь экран |

2.7. Для каждого экрана в остальных эпиках обязательно описываются четыре состояния: загрузка, пусто, ошибка, нет прав. Компоненты для них берутся из этого набора.

### Платформенные соглашения

2.8. Навигация реализуется средствами платформы, а не копированием чужой:
- **Мобильное приложение (iOS + Android)** — React Navigation (native-stack + bottom-tabs): на iOS это даёт нижнюю панель вкладок, навигационную панель сверху и переходы «вперёд-назад» со свайпом; на Android — нижнюю панель навигации, верхнюю панель приложения и системную кнопку «назад». Каждая платформа получает свои нативные компоненты навигации автоматически, без ручного дублирования макета;
- **Веб** — верхнее меню, адресная строка отражает состояние, работают кнопки браузера «назад» и «вперёд».

2.9. Основные разделы приложения одинаковы на всех платформах: Лента, Мои объявления, Чаты, Профиль.

2.10. Тёмная тема поддерживается на всех платформах и следует системной настройке.

2.11. Поддерживается системный размер шрифта: увеличение текста в настройках устройства не ломает верстку экранов.

### Макеты

2.12. Собрать кликабельные макеты пяти экранов в виде HTML-страниц:

1. **Лента объявлений** — переключение «рейсы / заявки», карточка в списке, панель фильтров, пустое состояние
2. **Карточка рейса** — маршрут, даты, свободный вес, цена за килограмм и минимальная стоимость, срок хранения, профиль курьера со статусом верификации и рейтингом, кнопка отклика
3. **Создание объявления** — форма по шагам и поле свободного ввода с разбором через ИИ, подсказка справочника весов
4. **Экран сделки** — все статусы, опись, два поля веса, фотографии, контакты передающего и получающего, кнопки подтверждения
5. **Профиль** — статус верификации, число сделок, рейтинг, отзывы, частые маршруты

2.13. Макеты показываются заказчику, правятся по замечаниям и утверждаются. Утверждённый вариант описывается словами в соответствующем эпике.

2.14. Макеты делаются в мобильной раскладке. Веб-раскладка выводится из них по правилам адаптивности, отдельные макеты для неё не рисуются.

### Тексты интерфейса

2.15. Все тексты интерфейса собираются в словари локализации в `/packages/shared` и на каждой платформе. Захардкоженных строк в коде быть не должно.

2.16. Зафиксировать правила тона: обращение на «вы» со строчной буквы, без восклицательных знаков, ошибки формулируются как подсказка к действию, а не как обвинение.

## Критерии приёмки

- [ ] Токены описаны в машиночитаемом виде и подключены на всех клиентах (веб, админка, мобильное приложение)
- [ ] Все компоненты из таблицы 2.6 реализованы на каждой платформе со всеми перечисленными состояниями
- [ ] Собрана демонстрационная страница (или экран) с показом всех компонентов во всех состояниях — по одной на платформу
- [ ] Тёмная тема работает и следует системной настройке
- [ ] Увеличение системного шрифта до максимального не приводит к обрезке текста и наложению элементов
- [x] Пять макетов собраны, показаны заказчику и утверждены им письменно
- [x] Утверждённые макеты описаны словами в эпиках E07, E08, E10, E06
- [ ] В коде клиентов нет строковых литералов, показываемых пользователю

## Зависимости

**Требует:** E01 в части структуры репозитория и пакета `shared`. Может выполняться параллельно.

**Блокирует:** клиентские задачи всех эпиков. Ни одна задача веб- или мобильного (React Native) трека не начинается, пока макеты не утверждены.

---

## Технические детали и ограничения

**Макеты делаются в HTML**, а не в Figma: результат получается быстрее, его можно показать и поправить в тот же день, и он не требует дизайнерского инструмента. Утверждённый макет — это ориентир для реализации, а не пиксельный эталон: каждая платформа собирает экран своими компонентами.

**Дизайнера в проекте нет**, визуальный язык собирался итеративно поверх готового брендборда, а не с нуля.

**Название — VEZZY. Визуальный язык утверждён (см. ниже).** Логотип — line-mark: подпись «VEZZY» шрифтом Manrope 800 плюс изогнутая линия маршрута с точкой-акцентом на конце (акцентный розовый). Палитра: Paper `#FAF5F3` (фон), Ink `#171F26` (текст), Primary Blue `#1E80B8` (доверие/акцент, бейджи верификации, аватары), приглушённый розовый `#B8506E` (основное действие — плоская заливка, без градиента и без эффекта стекла — оба варианта пробовались и были отклонены), нейтральные `#EFE6E0` (границы), `#6B6F76` / `#9AA0A8` (второстепенный текст). Радиус скругления небольшой — 6–10px для кнопок и карточек, не `rounded-full`. Герой главной страницы — мягкие радиальные градиентные пятна (синее и розовое) поверх фона Paper.

**Мобильное приложение — React Native (Expo), навигация — React Navigation** (native-stack + bottom-tabs). Один набор экранов и компонентов на JS/TS для iOS и Android вместо двух нативных кодовых баз; Expo (managed workflow, EAS Build) снимает требование к локальной установке Xcode/Android Studio для сборки.
