## Platform

adaptive

## Users

Курьер — путешественник, продающий свободное место в багаже; участник сделки, всегда с приложением (может действовать через доверенное лицо при передаче/приёме, но подтверждения в приложении делает только сам). Заказчик — вторая сторона сделки, платит за доставку, всегда с приложением; физически передающий или получающий посылку — по умолчанию заказчик, но может быть третьим лицом без приложения. Модератор — сотрудник сервиса, работает только в админ-панели (ручная верификация, жалобы). Целевая аудитория курьеров и заказчиков — русскоязычные экспаты 18+; приоритетные направления СНГ и Юго-Восточная Азия (пример коридора — Москва ↔ Нячанг).

## Product Purpose

P2P-сервис попутной доставки: путешественник, летящий по нужному маршруту, продаёт часть свободного места в багаже человеку, которому нужно передать или получить небольшую посылку между Россией и страной проживания. Успех — сделка завершена: посылка передана курьеру и вручена получателю, обе стороны подтвердили это в приложении.

## Positioning

Дешевле и быстрее СДЭК/карго — использует уже оплаченный багаж попутчика вместо отдельной логистической цепочки. Надёжнее телеграм-чатов — обязательная верификация личности по паспорту (модерируемая проверка документа, а не визуальный бейдж) как структурный источник доверия, которого у неформальных чатов нет.

## Operating Context

Продукт кросс-платформенный: мобильное приложение на React Native (Expo; iOS от 16, Android от 9 / API 28), веб-клиент (Next.js/React/TypeScript) и отдельное Next.js-приложение админ-панели для модераторов. Мобильное приложение полнофункционально; в вебе нет доступа к камере — фото документов и содержимого посылки загружаются файлом, остальное доступно. Единая точка входа для всех клиентов — REST API на NestJS; клиенты не обращаются к Supabase напрямую. Контракт API описан в OpenAPI-спецификации (packages/contracts) — единственный источник правды, из неё генерируется единый TypeScript-клиент для веба и мобильного приложения. Интерфейс только на русском, все тексты вынесены в файлы локализации на каждой платформе (без хардкода строк). Уровни доступа нарастают по мере вовлечения: просмотр лент и карточек — без регистрации, сообщения в чате — после регистрации, публикация объявления и вход в сделку — только после пройденной верификации.

## Capabilities and Constraints

MVP полный по составу (эпики E01–E16, порядок и зависимости — docs/tz/epic-00-overview.md), почти всё помечено must. Отложено за рамки MVP (обоснования — BACKLOG.md): пересылка местными службами доставки, эскроу и оплата внутри приложения, продуктовая аналитика, «купи и привези», автоматический KYC, поиск курьера по стране целиком, формальные споры с арбитражем, антиспам и лимиты, английский язык, конвертация валют, страхование посылки.

Деньги между пользователями идут мимо приложения — сервис не принимает, не хранит и не переводит деньги; цена в объявлении и сделке информационная. Модель данных уже спроектирована под будущий эскроу (цена, валюта, история статусов, подтверждения обеих сторон), чтобы добавление эскроу не потребовало переписывать ядро.

Персональные данные: сканы документов не хранятся — удаляются безвозвратно из хранилища после решения модератора; в базе остаются только флаг верификации, имя, фамилия, дата рождения, тип документа, хэш номера документа, дата и идентификатор проверки.

Тихие часы: несрочные уведомления не доставляются с 23:00 до 08:00 по местному времени пользователя (часовой пояс — из города в профиле либо из настроек устройства).

Модель ИИ для всех применений (модерация объявлений, модерация описи, разбор свободного текста, первая линия поддержки) — Claude Haiku 4.5.

Справочные величины MVP: 15 городов в 4 странах (Вьетнам, Россия, Казахстан, Киргизия) — 210 направлений; город означает место передачи посылки, а не аэропорт. 4 валюты (рубль, донг, тенге, сом) без автоматической конвертации. Возраст пользователей — 18+, проверяется по дате рождения при верификации.

Терминология: «отправитель» не используется — вторая сторона сделки чаще получает посылку, чем отправляет («заказчик»); «передающий»/«получающий» — роли физической передачи, отдельные от «курьер»/«заказчик».

## Product Principles

- Доверие через обязательную верификацию личности — структурное отличие от неформальных чатов, а не просто бейдж.
- Деньги вне контура сервиса в MVP, но модель данных заранее готова к эскроу — чтобы будущее не требовало переписывать ядро.
- Минимальное хранение персональных данных: сканы документов существуют только до решения модератора.
- Паритет платформ: мобильные клиенты полные, веб уступает только в работе с камерой.
- API-контракт (OpenAPI) как единственный источник правды для всех клиентов — контракт пишется раньше реализации клиентов.
